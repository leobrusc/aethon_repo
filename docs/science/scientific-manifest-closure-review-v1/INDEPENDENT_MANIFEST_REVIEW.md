# Independent manifest-boundary review

## Scope

Reviewed PR #27 at `2034aade9b56bf76ff13f4816a5ff9de73a879a6`, based on the PR #26 finding commit `26834be1e72f8e6f102a5431019b3f4cad1d4091`. The independent review worktree is branch `review/scientific-manifest-closure-v1`. No production backend, authorization, or scientific result was created.

## Disposition

No reproducible SCI-REV-01 scientific-manifest bypass was found. `StorageBackend.open_run` is the base template method and validates canonical manifest bytes, authorization identity, the full scientific manifest, authorization provenance, and retention before delegating to `_open_validated_run`. The metaclass rejects ordinary subclass and multiple-inheritance overrides of `open_run`; the synthetic backend creates no run state before that call.

However, adversarial review found a separate high-severity authorization defect, `AUTH-REV-01`: both `PrivateRunStore` and `StorageBackend.open_run` use `isinstance(authorization, Authorization)` and dynamically dispatch `authorization.check(subject)`. A subclass can override `check()` with a no-op, construct otherwise matching synthetic provenance fields, and reach the scientifically validated backend without being registered in `_ISSUED_AUTHORIZATIONS`. A synthetic reproduction emitted a capability and created one memory-backend run for an unissued authorization object. This does not accept a malformed scientific manifest, so SCI-REV-01 itself remains closed; it does bypass the operational authorization object gate and blocks native-backend readiness.

Minimal reproduction shape, using the existing synthetic fixture's valid manifest/config/subject and a fresh `MemoryBackend`:

```python
FakeAuthorization = type("UnissuedAuthorization", (Authorization,),
                          {"check": lambda self, subject: None})
fake = FakeAuthorization(subject_sha256, policy_sha256, receipts_sha256,
                         future_expiry, launch_sha256,
                         storage_custodian=custodian,
                         retention_delete_after=delete_after,
                         retention_plan_sha256=plan_sha256)
store = PrivateRunStore(manifest=valid_synthetic_manifest,
                        authorization=fake, backend=MemoryBackend())
assert store.run_capability is not None
```

Observed result: `issued_registry_contains_object=false`, `capability_created=true`, `backend_run_count=1`, `scientific_slots=120`. The reproduced manifest was scientifically valid; the defect is authorization provenance/issuance, not acceptance of malformed science.

This is an application boundary for trusted backend code. It is not a boundary against hostile code in the Python process: runtime monkey-patching, deliberate reflection, interpreter compromise, or a malicious native backend can defeat Python-level controls. The current memory backend is synthetic and is not production storage. AUTH-REV-01 requires ordinary subclass code, not interpreter compromise or monkey-patching, and should be fixed before any native backend.

## Scientific contract checked

- Inventory has exactly 24 unique cases and 12 distinct pairs, each containing one integer label `0` and one `1`.
- Pair family and legitimate task context agree; the three canonical families have exactly four pairs each.
- Unknown row/root fields, duplicate JSON keys in source inventory, duplicate sample/source/scenario identities, malformed identities, and non-finite JSON are rejected.
- The validator reconstructs all 120 slots, five conditions per case, exact slot projections, and the seeded schedule. It checks the exact schedule generated by the frozen seed and policy, not only the B3/B4 partial order.
- The immutable manifest is schema `aethon.pilot-run.v2`; v1/unknown schemas fail closed.
- The historical run fingerprint formula remains `fingerprint([subject, config, validated_rows, retention, order])`. The authorized raw inventory is base64-bound inside the private manifest and its SHA-256 is checked against the authorized subject. No hash is computed over slots as a substitute.
- Rejection tests assert no `_runs` or capability handles are created. A valid synthetic manifest opens/reopens idempotently and exercises 120 slots, journal recovery, pending scientific review, and fingerprint-gated B3/B4 reuse.

## Canonicalization and resource limits

The outer manifest must be canonical JSON byte-for-byte; parsing and re-encoding rejects duplicate outer keys and noncanonical encodings. The source inventory parser explicitly rejects duplicate keys and non-finite constants. The external reader caps source evidence at 10 MiB. `open_run` caps manifest bytes at the configured budget (default 2 MiB, ceiling 8 MiB); `bounded_json` enforces depth 48 and 100,000 nodes before canonical serialization. This bounds input sizes and structure, not process RSS against a compromised host or parser implementation.

## Private inventory confidentiality

`inventory_source_b64` is private run-manifest content and must remain inside an approved private backend. The preflight CLI emits only classification, execution state, and gate statuses; its error path prints a generic reason and does not print the returned runtime context, inventory, prompts, exceptions, or private paths. CI tests use synthetic fixtures. The workflow artifact allowlist contains only `results/security/audits/` and `results/validation/deterministic-*.json`; it does not upload run manifests or inventory directories. The PR #27 Windows CI log was searched for `inventory_source_b64`, `inventory_raw`, the private inventory schema name, and private-root arguments; all were absent. Artifact ZIP payloads were not independently unpacked in this review, so the artifact conclusion is based on workflow paths and their producing code.

## Residual requirements

Structural validation does not establish semantic correctness or human approval. A native backend must call this validator before issuing a capability, bind it to the trusted root, and implement atomic durable commit/recovery semantics. Fix AUTH-REV-01 by accepting only the exact base `Authorization` type (and invoking the non-virtual base check), or by using a separately sealed internal authorization token; test subclass and forged-instance rejection before backend state creation. The schedule uses the standard-library seeded shuffle; pinning an explicit PRNG/schedule algorithm in a future protocol version would improve long-term cross-Python reproducibility. Do not silently change an existing schedule.
